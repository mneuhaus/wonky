## What it is

The analytic surface/surface intersector (SSI) for pairs of "implicit" elementary surfaces: plane, cylinder, cone, sphere, torus. `IntPatch_ImpImpIntersection.cxx` (9,714 lines; it is several historic `.gxx` files concatenated) dispatches per pair. The classification and closed-form conic construction live in `IntAna_QuadQuadGeo.cxx` (2,918 lines). Non-conic quadric intersections are delegated to `IntAna_IntQuadQuad` / `IntAna_Curve` (quartic curves parameterized by the angle of a cylinder or cone). Cylinder/cylinder has its own closed-form parameterization plus a walking fallback (`CyCyNoGeometric`). In a Boolean it is reached via `IntTools_FaceFace::Perform` -> `IntPatch_Intersection::Perform` -> `GeomGeomPerfom` -> `IntPatch_ImpImpIntersection` (DOCUMENTED, code).

## How it works

### Dispatch (IntPatch_ImpImpIntersection::Perform, L2517-L3054)
- `SetQuad` (L3058-L3091) maps type -> code: plane 1, cylinder 2, cone 3, sphere 4, torus 5. Pair key `iTT = 10*i1 + i2`, with `bReverse = i1 > i2`. The switch (L2567-L2769) calls `IntPP` (11), `IntPCy` (12/21), `IntPCo` (13/31), `IntPSp` (14/41), `IntPTo` (15/51), `IntCyCy` (22), `IntCyCo` (23/32), `IntCySp` (24/42), `IntCyTo` (25/52), `IntCoCo` (33), `IntCoSp` (34/43), `IntCoTo` (35/53), `IntSpSp` (44), `IntSpTo` (45/54), `IntToTo` (55). Anything else throws `Standard_ConstructionError`. DOCUMENTED.
- Each routine turns the `IntAna_QuadQuadGeo` result into `IntPatch_GLine` objects (line/circle/ellipse/parabola/hyperbola), `IntPatch_ALine` (analytic non-conic), `IntPatch_WLine` (walked polyline) or `IntPatch_Point`.
- **Transition (orientation) rule, used everywhere:** at a reference point `P` with curve tangent `T`, `q = T · (n2(P) × n1(P))` (`DotCross`). `q > 0` gives `trans1 = Out, trans2 = In`, else the reverse. Several routines use a dead band `|q| <= 1e-8` -> `IntSurf_Undecided` (e.g. L4997-L5010, L5051-L5065). For tangent lines (`NbSol == 1`) the "situation" Inside/Outside is derived from the direction to the curvature center versus the normals (plane/cylinder L3203-L3255, cyl/cyl L4900-L4986). DOCUMENTED.
- **Post-processing (L2782-L2934):** unless the surfaces are the same, the other quadric's implicit function is evaluated along each face's boundary arcs (`IntPatch_ArcFunction` + `solrst.Perform(..., TolArc, TolTang)`). This finds restriction points and segments (`PutPointsOnLine`, `ProcessSegments`, `ProcessRLine`). If both faces have "all arc solutions" and equal type, or `SameSurf`, the result is "tangent faces". Then `oppo` = normals anti-parallel at a type-specific reference point (L2865-L2904). Isolated points are kept only if both `D1->Classify` and `D2->Classify` (TolArc) are not OUT (L2939-L2973). Closed circles/ellipses without vertices get two vertices at parameters 0 and 2π (L3000-L3052).
- Circles are re-framed to the quadric's seam via `AdjustToSeam` / `SeamPosition` (L3863-L3925): the circle's X axis is set to the cylinder/cone/torus `XDirection`, so parameter 0 lies on the seam.

### Classification formulas in IntAna_QuadQuadGeo (DOCUMENTED, code)
- **Inner tolerances** (`InitTolerances`, L351-L359): `EPSILON_DISTANCE = 1e-14`, `EPSILON_ANGLE_CONE = Precision::Angular() = 1e-12`, `EPSILON_MINI_CIRCLE_RADIUS = 0.01*Confusion = 1e-9`, `EPSILON_CYLINDER_DELTA_RADIUS = 1e-13` (relative), `EPSILON_CYLINDER_DELTA_DISTANCE = Confusion = 1e-7`, `EPSILON_AXES_PARA = 1e-12`. Precision constants from `Precision.hxx`: `Angular 1e-12`, `Confusion 1e-7`, `PConfusion 1e-9`, `Intersection 1e-9`, `Approximation 1e-6`.
- **AxeOperator** (L69-L231): parallel test `V1.IsParallel(V2, 1e-12)`. Distance = point-line distance if parallel, else `|normalize(a1×a2)·(o2−o1)|`. "Coplanar" requires distance < eps and `|det3(a1,a2,o1−o2)| <= eps`. `RefineDir` (L2867-L2918) snaps a direction with one component within `RealEpsilon` of ±1 to the exact axis. This is an ad-hoc cleanup of nearly axis-aligned inputs.
- **Plane/plane** (L389-L512): `vd = n1×n2`. If `|vd| <= TolAng` -> `Same` (both point-plane distances <= Tol) or `Empty`. Else a line through the average of two constructions `P_i + par_i*(n_i×vd)` with `par = dist/(1−(n1·n2)²)`. For `|vd| < 2e-6` rad it re-projects the origin with two line/plane intersections, because the comment documents 1e-4 errors at angles of 2e-6.
- **Plane/cylinder** (L543-L722), inputs plane `Ax+By+Cz+D`, axis origin `o`, axis `a`, radius `r`, optional face height `H`:
  - `dist = n·o + D` (signed axis-origin distance).
  - Parallel test: `IntAna_IntConicQuad(axis, plane, tolang, toltang, H).IsParallel()`.
  - If parallel: `omega = o − dist*n`. `||dist| − r| < Tol` gives one tangent line through `omega`. `|dist| < r` gives two lines `omega ± sqrt(r²−dist²)*(a×n)`. Otherwise empty.
  - If not parallel: center `c = axis ∩ plane`, `sint = |n×a|`. `sint < Tol/r` gives a circle of radius `r` framed with the cylinder X axis. Otherwise an ellipse: normal `n`, major direction `(n×a)×n`, major radius `r/|a·n|`, minor radius `r`.
  - **Near-parallel patch (PR #1176, 2026-03-31):** if the axis/normal angle exceeds 45° and deviates from 90° by more than `Tolang`, with `sinda = |sin(dangle)|`: when `|sinda − Tol| < Tol`, or `H > 0 && sinda*H < 2*Tol`, the pair is treated as parallel. `tolang = 2*sinda` and `toltang = max(Tol, 1.01*sinda*H)`. The line directions are then recomputed from projections of two axis points 100 units apart, so the returned lines are deliberately not parallel to the axis (L567-L668). The height-dependent classification is a tolerance device, not a geometric fact.
- **Plane/cone** (L752-L953): signed apex distance `dist`, `cost = |a·n|`, `sint = |n×a|`, `sina = |sin φ|`, `costa = cost*cos φ − sint*sina` (= cos(t+φ), zero when the plane is parallel to a generatrix).
  - Apex in plane (`|dist| < Tol`): one line if `|costa| < Tolang`, two lines if `cost < sina`, otherwise the apex point.
  - Otherwise: hyperbola if `cost < Tolang`; parabola if `|costa| < Tolang`; circle if `sint < Tolang`; hyperbola if `cost < sina`; else ellipse with radius `cost*sina*cos φ*d/(cost²−sina²)`.
  - Results with ellipse parameters > 1e9 or hyperbola parameters > 2e6 return `done = false`, which falls back to the bi-parametric intersector.
- **Cylinder/cylinder** (L1050-L1297), using AxeOperator with distance eps `1e-7` and angle eps `1e-12`:
  - Parallel axes: `d <= Tol` gives `Same` if `|R1−R2| <= Tol`, else `Empty`. `d > R1+R2+Tol` gives empty. `R1+R2−d <= RealSmall` gives an external tangent line. `d > |R1−R2|` gives two lines from circle/circle intersection, reduced to one tangent line if `4R1²sin²(∠AP1P2) < Tol²`. `d > |R1−R2| − Tol` gives an internal tangent line. Otherwise empty.
  - Non-parallel: equal radii (relative `1e-13`) with intersecting axes gives two ellipses. These are the planar "Steinmetz" cases with axes `a1±a2` and radii `R/cos(θ/2)`, `R/sin(θ/2)`, plus two multiple points at the ellipse vertices. `|d − R1 − R2| < Tol` gives a tangent point. Else `IntAna_NoGeometricSolution`.
- **Plane/torus** (L2163-L2249): only two configurations are analytic. Axis parallel to the plane normal gives circles of radius `R ± sqrt(r²−d²)`. Axis in the plane through the torus center gives two circles of radius `r` at `±R`. Anything else is `NoGeometricSolution`. The other `*To*` pairs are analytic only when coaxial (L2278-L2660). `TreatResultTorus` converts circles to GLines (ImpImp L9648-L9714).
- Result enum `IntAna_ResultType`: Point, Line, Circle, PointAndCircle, Ellipse, Parabola, Hyperbola, Empty, Same, NoGeometricSolution.

### Cylinder/cylinder general case (DOCUMENTED, `ComputationMethods`, L3949-L4250, L5197-L5445; `CyCyNoGeometric` L6573-L7880)
- Parameterize `S_i(U,V) = L_i + R_i cos U X_i + R_i sin U Y_i + V Z_i`. `S1 = S2` gives three equations. Pick the two with the largest `|C11 C22 − C12 C21|` (a cross-product component of the axes) and solve linearly for `V1, V2`: `V1 = K11 sinU1 + K21 sinU2 + L11 cosU1 + L21 cosU2 + M1` (same form for V2).
- Substituting into the third equation gives **`cos(U2 − FI2) = B cos(U1 − FI1) + C`**, so each U1 has two branches `U2 = FI2 ± acos(B cos(U1−FI1) + C)`. `ShortCosForm(a,b)` turns `a cos x + b sin x` into `k cos(x − φ)`. `CylCylComputeParameters` clamps the acos argument to ±1 within `aTol0 = min(10*eps*B, 1e-11)`. It also estimates the U2 error as `aTol0/sqrt(δ(2−δ))`, with δ the distance of the argument from ±1 (Taylor expansion of acos), i.e. the curve is ill-conditioned near branch points.
- The walker samples U1 over the admissible ranges (`BoundariesComputing` solves where the acos argument hits ±1) with adaptive steps. It uses 200-1000 points, or 50-200 for "good" cases (radius ratio > 3, axes within 10° of perpendicular, axis distance < Rmax/2). It returns `IntStatus_InfiniteSectionCurve` if the V range exceeds `1e5*R` (comment quotes issue #26894: "error not exceeding R/100" given 15 significant digits).

### Other quadric pairs (DOCUMENTED, `IntAna_Curve.cxx` L279-L377, `IntPatch_Intersection.cxx` L1778-L1905)
- When the QuadQuadGeo result is not a conic, `IntAna_IntQuadQuad` parameterizes by the angle θ of the cylinder or cone. The other quadric becomes `A(θ) v² + B(θ) v + C(θ) = 0`, where A, B, C are degree-2 trigonometric polynomials (`Z2Cte + Z2Sin sinθ + Z2Cos cosθ + Z2SinSin sin²θ + Z2CosCos cos²θ + Z2CosSin sin2θ`, same for Z1, Z0). The solution is `v = (−B ± sqrt(B²−4AC))/2A`, with the discriminant zeroed below `aTolD = 2*dT*|d(disc)/dθ|`.
- `GeomGeomPerfom` converts every such `IntPatch_ALine` into a 200-point `IntPatch_WLine` (`IntPatch_ALineToWLine`). IntTools later approximates it by a B-spline. **Only conics survive as exact curves in an OCCT Boolean result.**

### Gating (who gets the analytic path at all)
- `IntPatch_Intersection::Perform` (L1097-L1260) treats cones with semi-angle < 0.02 rad or > 1.55 rad, and tori, as bi-parametric (walking) unless the axis relations qualify: plane/cone always analytic unless the cone is nearly a cylinder and nearly parallel to the plane; torus only when parallel, or normal and through the axis; coaxial otherwise. Infinite domains force the analytic path.
- `IntTools_FaceFace.cxx` `isTreatAnalityc` (L249-L325): for plane/finite cylinder, if the analytic result is an ellipse with `major >= 1e5 * minor`, the analytic path is disabled and the walker is used.
- Tolerances passed down: `TolArc = TolTang = Tol(F1) + Tol(F2) + fuzzy` (each face tolerance plus half the fuzzy value, L381-L386). The default face tolerance is `1e-7`, so `2e-7`. `Tolang = 1e-8` is hard-coded for plane/plane and plane/cylinder.

## Robustness and guarantees

- Nothing is certified (DOCUMENTED by the code). Every topological decision (parallel, tangent, circle vs ellipse, same surface, apex in plane) is an f64 comparison against a constant or against the sum of face tolerances. There is no error analysis of the discriminants. Epsilons span `1e-14` (absolute) to `1e-7` and are mixed with relative ones (`1e-13*Rmax`).
- Degenerate and near-degenerate cases are resolved by **reclassification to a nearby simpler configuration**: near-parallel becomes lines, near-circle becomes a circle, near-tangent becomes a tangent line. The resulting deviation is absorbed by edge and vertex tolerances later (`IntTools_FaceFace::ComputeTolReached3d`). This is tolerance growth, not a decision (DOCUMENTED, L613-L700).
- Undecidable transitions are labeled `Undecided` (dead band 1e-8). Non-conic curves are sampled polylines. `CylCylComputeParameters` provides an error estimate but only for step control, not as a bound on the output.

## Parallelism and performance

- ImpImp is a pure per-face-pair computation. The Boolean runs all face/face pairs in `BOPAlgo_PaveFiller::PerformFF` through `BOPTools_Parallel::Perform(myRunParallel, aVFaceFace)` (`TKBO/BOPAlgo/BOPAlgo_PaveFiller_6.cxx:529`, DOCUMENTED). No published timing for ImpImp alone was found. Expected (INFERRED): the analytic path is O(1) per pair plus boundary-arc root finding. The walker fallbacks (200-1000 points) dominate.

## Known failures, limitations, war stories

- PR #1176 (merged 2026-03-31, commit 797d325): plane/cylinder faces of small height were misclassified as non-parallel. The fix introduced the H-dependent tolerance relaxation above. https://github.com/Open-Cascade-SAS/OCCT/pull/1176 (DOCUMENTED).
- PR #1228 (merged 2026-04-28, commit bea50c2): "2 cylinders are tangent along a line. The analytical intersection returns a point which is not valid". The fix routes the case to the implicit-implicit walker and adds 424 lines of GTests (`TKBO/GTests/IntTools_FaceFace_Test.cxx`) including argument-order independence. https://github.com/Open-Cascade-SAS/OCCT/pull/1228 (DOCUMENTED).
- Issue #1543 (open, 2026-09-16): `BRepAlgoAPI_Cut(cylinder, helical sweep)` silently removes nothing depending only on where the tool crosses the top face relative to the cylinder seam. "IntPatch loses the boundary vertex after seam decomposition"; rotating the cylinder 90° fixes it. https://github.com/Open-Cascade-SAS/OCCT/issues/1543 (DOCUMENTED). Seam handling of periodic quadrics is a live failure source.
- Issue #26894 (legacy Mantis, quoted in code L6594-L6601): infinite non-analytic section curves must fail explicitly. OCCT caps the extent at `1e5*R`.
- The code comments themselves document numeric pathologies: the plane/plane origin error of about 1e-4 at small angles (L449-L462), and the acos cancellation giving `acos(aPar) − aFI2 = 2.16e-9` although the argument is exact to `5e-15` (L5363-L5373).

## Relevance for wonky

- **Direct prior art for the blocker.** A plane/cylinder union needs exactly `IntPCy`: 0/1/2 lines, a circle, or an ellipse. wonky already represents all of these. The OCCT decision tree maps one-to-one onto exact sign tests (INFERRED). Let `s = n·a`, `w = n×a`, `d = n·(o − p)` (plane point `p`), with unnormalized F32x2 inputs:
  - parallel ⇔ `s == 0`;
  - circle ⇔ `w == 0`;
  - for parallel, the line count comes from `sign(d² − r²·|n|²)` (`d` unnormalized, so this compares the true distance `|d|/|n|` with `r` without a square root or division);
  - tangency ⇔ that discriminant is exactly zero.

  Each is a polynomial in the input words. With F32x2 = two F32 words, the product of two F32x2 values is an exact 4-term F32 expansion. Degree-4 predicates therefore fit a multi-limb U32 integer or expansion arithmetic after scaling to a common exponent. Constructions (ellipse center `o + a·(n·(p−o))/s`, semi-axes `r` and `r|a||n|/|s|`) are rational/sqrt and can be produced in F32x2 with an a posteriori residual bound. Unlike OCCT, the topology comes from exact signs and only the embedding carries a tolerance.
- **Near-parallel planes/cylinders are common in FDM code** (e.g. a slightly rotated sketch plane). OCCT's answer (#1176, the 1e5 eccentricity cutoff) shows that a very eccentric ellipse is the true geometry and "lines" are a tolerance fiction. wonky should keep the exact ellipse when `s != 0`. If downstream evaluation of that ellipse cannot meet the requested tolerance in F32x2 (conditioning ~ eccentricity), it should return `Unresolved{reason: IllConditionedEllipse}` instead of silently switching topology (INFERRED, per project rule "fail explicitly").
- **Constants do not transfer to F32x2.** F32x2 unit roundoff is about 2^-48 ≈ 3.6e-15 relative. At 100 mm coordinates the absolute resolution is about 3.6e-13 mm, so OCCT's `1e-14` absolute and `1e-13` relative epsilons are below representable resolution. `Precision::Angular = 1e-12` is marginal. `Confusion = 1e-7 mm` is fine. Every OCCT epsilon test must become either an exact multi-limb sign test or an explicit F32x2 error-bound test with an `Unresolved` band (INFERRED).
- **Transition sign** `T·(n2×n1)` is the orientation predicate wonky needs to direct section edges before face splitting. It is exact-computable for conics at rational points. Zero means a tangent section, which must be routed to the contact machinery (`curved-contact.bend`), never to `Undecided` defaults.
- **Cylinder/cylinder** (FDM: cross-drilled holes, pins, T-joints): the analytic subcases (parallel lines, equal-radius intersecting axes giving two planar ellipses) are cheap wins. The general quartic has a clean closed-form parameterization `U2 = FI2 ± acos(B cos(U1−FI1) + C)`, V linear in sin/cos. wonky could store the curve as "exact defining quadric pair + branch index + certified polyline/spline with Hausdorff bound", instead of OCCT's anonymous WLine. The 1e5·R extent cap maps to an explicit `Unbounded` failure.
- **Bend fit:** every pair routine is a pure function of two small records. It is a natural `map` over candidate face pairs (balanced fork-join), and uniform enough for a GPU batch when grouped by pair type. The sampling in `CyCyNoGeometric` and `IntAna_Curve` is an embarrassingly parallel map over θ samples followed by a sequential chaining step. Rewrite the chaining as a scan or a tree merge.
- **Plugs into:** Boolean SSI (now), fillet (a plane/torus pair appears as soon as fillets exist), testing (port OCCT's `IntTools_FaceFace_Test.cxx` scenarios as fixture ideas, not code).

## Verdict: adapt

Port the **case analysis and closed-form constructions** (plane/cylinder, plane/cone, cylinder/cylinder special cases, plane/torus, coaxial pairs), re-deriving every decision as an exact sign predicate over F32x2 inputs with an explicit `Unresolved` band. Do not copy the tolerance heuristics: RefineDir snapping, H-dependent parallelism, eccentricity cutoffs, tolerance growth. Use the cylinder/cylinder closed form as the reference for a certified non-conic curve type. Code must not be copied (LGPL); wonky's rules already forbid linking.
