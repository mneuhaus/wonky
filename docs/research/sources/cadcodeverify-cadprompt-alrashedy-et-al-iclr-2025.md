## What it is

DOCUMENTED: a VLM self-review loop for natural-language→CadQuery Python→STL, and 200 expert-annotated prompt/code/shape examples drawn from DeepCAD. The central method generates its own verification questions and answers them against multi-view renders, then rewrites code from the unresolved answers. It is not a symbolic proof system despite “Verify” in the name. The geometric-solver comparison arm is a separate **ground-truth-assisted** baseline, not the method's normal runtime. [PDF §§3–5, pp.3–7](https://arxiv.org/pdf/2410.05340v2#page=3).

## How it works

1. DOCUMENTED: generate code y0 from prompt x, optionally with demonstrations from 40 CadQuery documentation examples. Execute with CadQuery; if it fails, send the generated code and compiler/runtime error back to the model, bounded by a maximum retry count N (no fixed numeric N found in the inspected methodology). Separately perform two geometry refinement stages, M=2. [§3, equations 1–3](https://arxiv.org/pdf/2410.05340v2#page=4), [Appendix B.3–B.4](https://arxiv.org/pdf/2410.05340v2#page=14).
2. DOCUMENTED: generate **2–5 Yes/No questions** based on the original description, with two few-shot question examples. Rules: No should indicate a needed modification; do not invent entities; avoid relative left/right orientation questions. Provide four renders at nominal 0/90/180/270° angles, original description and questions. Answer Yes/No/**Unclear** with short explanatory support. [§3.3](https://arxiv.org/pdf/2410.05340v2#page=4), [question prompt Fig.11](https://arxiv.org/pdf/2410.05340v2#page=21), [answer prompt Fig.13](https://arxiv.org/pdf/2410.05340v2#page=23).
3. DOCUMENTED: omit Yes answers from corrective feedback; convert No/Unclear into a few specific corrections while preserving already-satisfied requirements. If all answers are Yes, stop. Feedback instructions explicitly avoid asking for scale-reference objects, scale fixes or missing dimensions. INFERRED: this naturally checks appearance/qualitative structure better than dimensioned FDM fit; all-Yes is a self-judged stop condition, not independent evidence. [equations 4–5](https://arxiv.org/pdf/2410.05340v2#page=4), [Fig.14](https://arxiv.org/pdf/2410.05340v2#page=23).
4. DOCUMENTED: FreeCAD “geometric solver” baseline extracts 13 fields from generated and GT shapes and asks an LLM to verbalize differences: face/unique-edge/vertex counts, width/height/depth, bbox center, XY/XZ/YZ aspect ratios, solid flag, volume, surface area. Fig.6 omits the solid field in its illustrated payload, while released `Ground_Truth.json` includes it. These are generally **mesh-derived counts**, not an invariant analytic B-rep face count. [§5.1](https://arxiv.org/pdf/2410.05340v2#page=6), [Appendix B.2/B.5](https://arxiv.org/pdf/2410.05340v2#page=14), [sample metadata](https://github.com/Kamel773/CAD_Code_Generation/blob/33dcecd6087ff7b8a4454b1ba4d56504a6364399/CADPrompt/00005721/Ground_Truth.json).
5. DOCUMENTED: evaluation converts STLs to 1,000-point clouds, rigidly ICP-aligns, then normalizes clouds into a unit cube. Symmetric average nearest-point Euclidean distance is `D=(Σp minq ||p−q||)/(2|P|)+(Σq minp ||q−p||)/(2|Q|)`; Hausdorff uses the maximum directed nearest-point distance. “Intersection over Ground Truth” is described as overlap of bounding boxes, divided by GT extent/area, **not solid volume IoU**. Compile failures receive distance √3 and IoGT 0. INFERRED: normalized distance and bbox overlap cannot establish millimeter accuracy, watertightness, topology or assembly suitability. [§5.2, equations 8–10](https://arxiv.org/pdf/2410.05340v2#page=7), [B.3 point sampling](https://arxiv.org/pdf/2410.05340v2#page=14).

## Robustness and guarantees

DOCUMENTED: on 50 GPT-4 few-shot examples, manual review of generated answers reports **64.6% correct / 8.8% incorrect / 26.6% Unclear** at Refine 1 and **68.2% / 12.5% / 19.3%** at Refine 2. Important correction: 64.6/68.2 are not error rates among definite answers; Unclear occupies much of the remainder. Table 9 lists 219/176 total answers but its prose denominator for Refine 1 says 214 and is internally inconsistent with the percentages. Do not silently present a reconstructed clean accuracy statistic. [§6 p.10](https://arxiv.org/pdf/2410.05340v2#page=10), [Table 9 p.18](https://arxiv.org/pdf/2410.05340v2#page=18).

DOCUMENTED: geometric-solver feedback has privileged GT access and is called an upper-bound method by the authors. Its GPT-4/Gemini distances are better in Table 2, but **it is not a universal empirical upper bound**: CodeLlama's numerical-feedback arm has worse compilation/distance than CADCodeVerify. INFERRED: the study supports using reliable measurements, but does not isolate “numeric feedback always beats vision” or show that metrics without GT provide the same benefit. Compare numeric+GT against visual-without-GT carefully. [§5.1 and Table 2](https://arxiv.org/pdf/2410.05340v2#page=8).

DOCUMENTED: authors explicitly warn that small gaps separating a desk's legs and top can still give low point/Hausdorff distance while breaking logical structure; prompt wording and ambiguous descriptions materially affect results. No formal tolerance budget or geometric soundness theorem is provided. [§7](https://arxiv.org/pdf/2410.05340v2#page=10).

## Parallelism and performance

DOCUMENTED reported experiment results (not reproduced): GPT-4 few-shot CADCodeVerify best-refine median point distance 0.127 vs 3D-Premise 0.137 (7.30% relative reduction); compile 96.5% vs 91.0% (**5.5 percentage points**). Raw GPT-4 few-shot generated compile rate was already 96.0%, so 5.5 points is versus the other refinement baseline, not initial generation. Gemini best rates reach 85%, CodeLlama 73.5%; do not generalize these as universal model capability rates. Table 2 reports best-refine; appendix Tables 5–7 show later stages can regress. [Tables 2/5–7](https://arxiv.org/pdf/2410.05340v2#page=8), [appendix results](https://arxiv.org/pdf/2410.05340v2#page=17).

DOCUMENTED: Hard-subset prose reports roughly 20% compile-rate drop under 3D-Premise (to 62% at Refine 1). Human-feedback ablation on 50 examples improves point/Hausdorff distances from CADCodeVerify 0.137/0.445 to 0.120/0.397; compile 98.5%→99.0%, while CADCodeVerify's IoGT is slightly higher. This is a small comparison, not a blanket human-vs-agent theorem. [Fig.4 discussion p.8](https://arxiv.org/pdf/2410.05340v2#page=8), [Table 4 p.9](https://arxiv.org/pdf/2410.05340v2#page=9).

DOCUMENTED: experiments described as January–February and May–August 2024; generation/refinement temperature 0 for GPT-4/Gemini and repair temperature 1, CodeLlama-70B temperature 0.8; no kernel throughput benchmark or Bend/GPU algorithm. Main text names Gemini 1.5 Pro while appendix specifies `gemini-1.5-flash-latest`, and GPT endpoint is labeled `gpt-v4`, limiting exact reproducibility. Sample/model calls are independent across tasks, refinement within a task sequential. [Appendix B.3](https://arxiv.org/pdf/2410.05340v2#page=14).

## Known failures, limitations, war stories

- DOCUMENTED: released repository contains 200 `Python_Code.py` CADPrompt samples, an additional symmetrical ground-truth script, prompts, OBJ/STL/JSON and figures; **no CADCodeVerify runner or geometric-feedback/evaluation implementation found**. [Issue #1](https://github.com/Kamel773/CAD_Code_Generation/issues/1) asks for promised method code; comments through September 11, 2026 repeat the request with no author release reply in the retrieved thread. Do not call this a reproducible reference implementation.
- DOCUMENTED + INFERRED by code inspection: sample `00005721` asks for an “obtuse scalene triangle” but points `(0,0),(0,width),(length,0)` encode a right triangle. Script rotates/translates it, which cannot change its internal right angle. This is one concrete prompt/ground-truth inconsistency, not a measured corpus-wide error rate. [prompt](https://github.com/Kamel773/CAD_Code_Generation/blob/33dcecd6087ff7b8a4454b1ba4d56504a6364399/CADPrompt/00005721/Natural_Language_Descriptions_Prompt.txt), [script](https://github.com/Kamel773/CAD_Code_Generation/blob/33dcecd6087ff7b8a4454b1ba4d56504a6364399/CADPrompt/00005721/Python_Code.py).
- DOCUMENTED: Appendix C's taxonomy includes structural configuration, spatial precision, logical error, correct, and compile failure (not just three categories). Three annotators majority-voted 50 examples; configuration 48%, logical 18%. Useful for test labeling, not geometric definitions. [Appendix C p.16](https://arxiv.org/pdf/2410.05340v2#page=16).

## Relevance for wonky

INFERRED: retain the **requirement decomposition**, explicit Unclear and separate execution-vs-design-error loops. Replace visual answers to measurable questions with executable FS assertions: hole count/diameter/axis, required material at points, separation/intersection, bbox/volume deltas and validity coverage. Pair exact/interval numeric checks with renders for morphology and occlusion. Never let self-generated all-Yes certify dimensions or FDM readiness. A measure-first policy is a reasonable design inference, not a directly controlled finding of this paper. [method](https://arxiv.org/pdf/2410.05340v2#page=4), [answer reliability](https://arxiv.org/pdf/2410.05340v2#page=18).

INFERRED Bend fit: outer VLM coordination can stay in the JS frontend, while all actual geometry/evidence is computed in Bend. Counts are U32; integral reductions and distances need scale-aware F32x2; adjacency/topology and predicates need multi-limb exact checks where appropriate. Independent view renders, sample distances and requirement probes suit balanced fork-join; per-task correction remains sequential; none requires copying Python's mutable CadQuery/OCC object graph or linking FreeCAD. Original code assumes ordinary Python floating point and kernel tolerances with no F32 qualification. No SSI, Boolean or fillet algorithm is contributed. Dataset/license limits favor newly authored dimensioned wonky regression fixtures inspired by the taxonomy rather than importing the whole corpus. [sample numeric code](https://github.com/Kamel773/CAD_Code_Generation/blob/33dcecd6087ff7b8a4454b1ba4d56504a6364399/CADPrompt/00005721/Python_Code.py), [method and metrics](https://arxiv.org/pdf/2410.05340v2#page=7).

## Verdict: learn-from

Useful empirical warning against visual self-certification and a concrete blueprint for requirement-by-requirement review. Not an implementation to adopt: verifier code absent, repository license unspecified, reproducibility inconsistencies, and GT-assisted comparison is not a fair proof of universal numeric superiority. Open: method code/license clarification and independent, dimensioned numeric-vs-render ablation on wonky fixtures.
