## What it is
DOCUMENTED: a finite-output-precision segment arrangement algorithm now associated with snap rounding. Find the actual intersections, round their coordinates to a fixed grid, then also bend nearby segments through those same grid vertices. This second operation prevents crossings that **rounding intersection coordinates alone creates**. It produces a consistent planar arrangement of grid-vertex polylines, not an exact copy of the original straight segments. [Paper §§1–2, Figs.1–3](https://9p.io/who/hobby/93_2-27.pdf).

## How it works
**DOCUMENTED core construction (§2 and §4):**
1. Scale the chosen grid to integer spacing. Rounding is [x]=floor(x+1/2), applied coordinatewise. The tolerance square associated with grid vertex P is P+R where R=[-1/2,1/2)². The half-open boundary convention is essential: left/bottom included, right/top excluded. Thus this is not ties-to-even rounding.
2. Let T contain all segment endpoints and true intersections. Compute the unique rounded grid points [T]; these identify the tolerance squares, often called hot pixels in later literature.
3. For **each original segment**, find every hot pixel it intersects, including pixels whose generating event was on some other segment. Insert the pixel center into that segment's output chain, in traversal order, and join consecutive distinct centers. Do not only snap the intersections originally involving that segment.
4. The proof formalizes the result with R⁻=(-1/2,1/2]². A output edge AB is produced between consecutive grid centers from [T] intersected by the thickened source segment s+R⁻. R and R⁻ have opposite boundary inclusions because one describes which points round to a pixel and the other describes which pixel centers are incident to a segment. [Paper §§2,4](https://9p.io/who/hobby/93_2-27.pdf).

**DOCUMENTED practical two-pass implementation:**
- Pass 1 is a modified Bentley–Ottmann sweep, recording starting, stopping and actual crossing/swap events. It runs at least half a grid unit ahead of Pass 2: an event rounding to x=i can occur almost at i+1/2, after a relevant segment has ended at i. Querying the current sweep only at the rounded event coordinate misses such cases.
- Pass 2 groups events by rounded x coordinate i. Batch i has horizontal top/bottom pixel edges from i−1/2 to i+1/2. Maintain a main active-segment list and a separate tolerance-edge list. The vertical slabs between i−1/2, i and i+1/2 are called hammocks; segment-square crossings can be delayed until the end of a hammock.
- **Algorithm 1:** collect Batch i events; sort pixel top/bottom edges by y and insert centers for segments crossing the pixels at the left boundary; update the main list to i−ε; reconcile segment/tolerance-edge order at i, inserting centers on crossings; update to i+1/2−ε, handling vertical segments by walking crossed tolerance edges; reconcile again at i+1/2. Pass 1's recorded insert positions let Pass 2 use doubly linked lists rather than a second balanced search tree.
- Insert centers in ascending y for positive-slope segments and descending y for downward segments; the ordering of list walks matters. When crossing segments trap tolerance edges between them, relocate those edges and emit the corresponding centers rather than discarding the relationships. [Paper §2.1, Algorithm 1, Figs.4–5](https://9p.io/who/hobby/93_2-27.pdf).

**DOCUMENTED degeneracy and numeric model:**
- Conceptually tilt the sweep infinitesimally; shorten each segment at both ends by a doubly infinitesimal amount. This avoids endpoint intersections in Pass 1; Pass 2 still recovers them via endpoint pixels. At tied events: ending before crossing before starting. A point exactly at a horizontal pixel edge counts as above that edge, matching the half-open square.
- Ignore a queued crossing if its two segments are no longer adjacent. It is rescheduled when adjacency is restored. Theorem 2.2 allows crossing events not to be totally ordered against one another, while respecting the needed ordering against endpoints; for the combined algorithm they must still be ordered by rounded x batch. This is **not permission to use arbitrary wrong predicates**.
- If integer coordinate magnitudes are ≤L and each segment's coordinate span ≤LΔ, intersection denominators are <2LΔ². The paper derives sufficient relative accuracy about 1/(2LLΔ²) for comparisons with integers, and 1/(4LLΔ²) for the required half-integer comparisons. Slope order needs the exact sign of AΔy·BΔx−AΔx·BΔy. Bounds, not the name of a floating type, determine whether the computation is safe. [Paper §2.2, Eq.(1), Theorem 2.2](https://9p.io/who/hobby/93_2-27.pdf).

## Robustness and guarantees
- **DOCUMENTED theorem:** a segment set is fully intersected when every pair of unequal segments meets only at endpoints or not at all. Theorem 4.1 says discretization D_T of a fully intersected segment set, using T as its endpoints, is again fully intersected. This rules out unresolved crossings and partial overlaps in the resulting arrangement. Identical output segments can occur and need a policy for coincident labels. The theorem is not a general 3D snapping theorem. [§4](https://9p.io/who/hobby/93_2-27.pdf).
- **DOCUMENTED limitation:** the topology relationship is weaker than Greene–Yao's: two redrawn original segments may have an intersection that is a set of disjoint line segments, rather than one connected point/polyline. The no-interleaving property is preserved. Multiple nearby intersections can collapse to one grid vertex. Thus “preserves topology” without qualification is false; homeomorphism/isotopy to the original arrangement is not the guarantee. [§3 and conclusion pp.14–15](https://9p.io/who/hobby/93_2-27.pdf).
- **DOCUMENTED + INFERRED metric interpretation:** the proof places each output subsegment inside s+R⁻. With physical spacing h, this means an L∞ displacement bound of h/2 from the source segment; the corresponding Euclidean bound is h/√2, **not h/2**. Independent pre-quantization of input endpoints or later coordinate conversion consumes additional error budget. [§4, proof of Lemma 4.3](https://9p.io/who/hobby/93_2-27.pdf).
- DOCUMENTED: the theorem does not require original endpoints on the grid; it also supports rounding to a coarser grid. The practical finite-arithmetic analysis in §2 assumes integer endpoints. Do not transfer that arithmetic bound unchanged to arbitrary input reals. [§5](https://9p.io/who/hobby/93_2-27.pdf).

## Parallelism and performance
DOCUMENTED: total time is O((n+k) log n+k′), where k counts original intersections and k′ segment–tolerance-square incidences. Per batch O(N_i log N_i+k′_i); removing sorting would yield O(N_i+k′_i). k′ can approach the trivial n(n+k) bound for nearly collinear segments. The method is not unconditionally near-linear. [Theorem 2.1, §2.3](https://9p.io/who/hobby/93_2-27.pdf).

DOCUMENTED measurements: C++ on SGI 4D/380S with 33 MHz MIPS R3000 processors, nine small degenerate cases plus U.S. map-data cases. Table 1's largest case: n=52,359, k=35,694, k′=36,418; Bentley–Ottmann 37.80 s, combined algorithm 46.64 s (1.23× total). Smallest: n=297, 0.07 s versus 0.12 s (1.71× from rounded table values; text quotes 1.73×). These are historical serial timings, not evidence of parallel scaling. A naive repeated find/snap loop on one case takes 14.02 s versus 4.94 s for the tolerance-square method and adds fewer vertices, illustrating the runtime/output-size tradeoff. [§3, Table 1](https://9p.io/who/hobby/93_2-27.pdf).

INFERRED: the published sweep's mutable ordered lists and serial event schedule are a poor literal Bend/GPU port. The **geometric hot-pixel construction** is separable from that sweep and can instead be implemented as immutable batched detection, exact classification, sorting, deduplication and per-segment chain generation.

## Known failures, limitations, war stories
- DOCUMENTED: Figs.1–2 provide a regression case where snapping one true intersection to (5,3) introduces extra intersections; repeated repair eventually stabilizes in that example but lacks a small iteration-count guarantee. Input endpoints include (0,0), (9,5), (−1,−2), (13,6). [§1](https://9p.io/who/hobby/93_2-27.pdf).
- DOCUMENTED: coarse grid choices increase merged intersections and extra inserted vertices; almost-collinearity can explode k′. [§§2.3,3](https://9p.io/who/hobby/93_2-27.pdf).
- INFERRED: using a closed square, ties-to-even, missing endpoint hot pixels, or sorting centers only by rounded intersection parameter can break the stated construction. These are implementation hazards inferred from the half-open convention and Algorithm 1, not reported upstream issues.
- No source repository/issue tracker was examined for this paper; do not attribute behavior of unrelated snap-rounding libraries to Hobby's implementation. No original test corpus or runnable code obtained.

## Relevance for wonky
**INFERRED design from the cited paper and supplied Bend constraints:**
- Best placement: explicit finite-grid **2D section/sketch arrangement output**, contour preparation, or an opt-in tolerance mode for FDM. Keep it separate from the analytic B-rep Boolean that must retain exact surfaces. It bends lines, can remove narrow faces and merge intended clearances; that is a product-level semantic decision, not harmless serialization.
- Prototype a pure batch algorithm: (1) exact bounded-width segment-pair predicates and rational intersections; (2) create/sort/unique endpoint and intersection grid IDs; (3) conservatively AABB-filter segment–hot-pixel pairs, then classify exactly; (4) group by source segment and sort by monotone traversal key; (5) remove repeated centers, emit edges, retain all contributing source IDs on coincident edges. An all-pairs version is simple but O(n²+nH); spatial partitioning should follow only after correctness. This differs from the published sweep and does not inherit its complexity bound.
- Use U32 limbs for cross products and rational-vs-half-integer tests. For x=N/D, first make D positive; testing against q+1/2 becomes the exact sign of 2N−(2q+1)D. Do not round x to F32 before deciding the hot pixel. Derive limb width for the entire expression and reject ranges that overflow it. No f64, FFI or dynamic expansion is required in this formulation.
- Preserve grid integers as topology keys. F32 can exactly store consecutive integers only through magnitude 2^24. Power-of-two spacing plus a local coordinate frame helps, but converting to a huge global origin can erase a cell step; certify or reject the output conversion independently. F32x2 is an optional evaluation/output tier, not a substitute for integer cell identity.
- Uniform kernels can process fixed-size segment-pair and segment-pixel candidates in balanced fork-join passes. Sorting/grouping requires a pure parallel implementation and output cardinality budgets. Avoid dynamic event queues on GPU.
- Make tolerance and loss visible: grid origin/spacing, norm, geometric deviation bound, collapsed vertices/edges/faces, coincident-edge provenance and lost minimum clearances. If the user expects exact identity or a feature exceeds its budget, fail explicitly. For Euclidean error budget δ from snapping alone, choose h≤√2·δ, with stricter limits after accounting for all other approximations.

## Verdict: adapt
Adopt the hot-pixel construction for an **explicitly approximate planar-output path**; adapt its scheduling to pure batch operations. Do not silently apply it to analytic geometry or claim exact topology preservation. The half-pixel bound is coordinatewise, and representing the output safely as F32 needs a second range/rounding contract.
