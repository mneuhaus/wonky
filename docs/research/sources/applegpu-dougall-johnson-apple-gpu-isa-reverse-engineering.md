## What it is

DOCUMENTED: the README calls this a messy work in progress reflecting the author's understanding of Apple G13 (M1). The emulator is neither a standalone product nor a final API. It provides a very useful *executable hypothesis about hardware behavior*, not an Apple conformance specification for all GPU families. Hardware tests replace shader code in Metal binary archives and compare hardware register/memory bits against the emulator ([README](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/README.md)).

## How it works

**Bit-exact operand path.** DOCUMENTED: `FloatSrcDesc.evaluate_thread_float` reads operand bits, widens half with `f16_to_f64(...,ftz=False)` and single with `f32_to_f64(...,ftz=True)`, then applies abs/negation modifiers. The F64 values here are mostly *encoded integer bit patterns* consumed by a software model, not a requirement that the GPU executes F64. `FSaturatableInstructionDesc.saturate_and_set_thread_result` converts back to half without FTZ or single with FTZ. Optional saturation maps negative/NaN to zero and values above one to one. Sources: [operand decoding](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/applegpu.py#L1316-L1351), [destination handling](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/applegpu.py#L3198-L3207).

**Floating ALU model.** DOCUMENTED: `FMAdd32InstructionDesc` calls `bfma64(a,b,c,ROUND_TO_ODD)`, then explicitly rounds/flushes through binary32. `FAdd32` uses the same model with multiplier one; `FMul32` with addend zero. The final F32 conversion uses `do_rounding` whose default table is **round-to-nearest, ties-to-even**. Thus RTNE is documented in the executable model; it is not merely a forum rumor. Conversely, the internal round-to-odd is a software intermediate-rounding technique, **not evidence that hardware F32 arithmetic rounds to odd**. Sources: [float instructions](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/applegpu.py#L3210-L3370), [rounding tables](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L78-L144), [F32 conversion](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L194-L247).

**Software fused arithmetic.** DOCUMENTED: `bfma64` splits sign/exponent/mantissa, makes an integer product, aligns the addend with sticky-bit compression (`shr_compress`), adds/subtracts integer significands, normalizes, and rounds. It explicitly handles zero, infinity and NaNs. Python arbitrary-size integers support its 128-bit-scale temporaries; they are not primitive Bend scalars. The code supplies useful reference algorithms for guard/round/sticky-bit handling. Source: [fma.py lines 280–399](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L280-L399).

**FTZ detail.** DOCUMENTED: single inputs with exponent field zero become signed zero, even if the fraction bits are nonzero. During F64-to-F32 conversion with `ftz=True`, a rebased exponent `<=0` zeroes exponent and fraction before final significand rounding. Therefore do not reduce the model to a vague 'small numbers are inaccurate': subnormal *inputs*, subnormal *results*, and the threshold ordering are individually observable behaviors. Half operands follow a different path. Source: [conversion functions](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L171-L278).

**Integer/float conversions.** DOCUMENTED: `ConvertInstructionDesc` names `u32_to_f`, `f_to_u32`, signed and smaller-width modes. Its rounding field labels 0 as `rtz` and 1 as `rte`, but a TODO says this is based on observed values and Metal does not allow choosing the round mode; possible meanings for 2 and 3 are speculation. There is no implemented conversion execution path in this class that proves those modes. Source: [convert descriptor](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/applegpu.py#L2657-L2693).

## Robustness and guarantees

DOCUMENTED scope: tested reverse engineering, not a proof that every F32 operation on every Apple GPU is FTZ/RTNE under every compiler setting. The source clearly models FTZ for the ordinary single ALU paths studied here. Moves, integer bitcasts, texture operations, transcendental approximations, conversions and later GPU generations must not inherit that claim without separate evidence. The test header explicitly asks for better float edge-case combinations and mutation checks demonstrating that breaking FTZ/rounding actually breaks the tests ([hwtest.py](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/hwtest.py#L10-L15)); README likewise calls coverage scattershot.

INFERRED: TwoSum/TwoProd proofs that assume gradual underflow cannot be imported unchanged. An F32x2 low word or expansion component whose nonzero bits fall below the normal F32 threshold can disappear when consumed or produced on these paths. The exact fallback should decode original bit patterns using integers, not multiply a subnormal by a large float after FTZ has already erased it. Use the executable model to design tests, but require actual compiler/target qualification before asserting a production numerical contract. Source basis: [float source](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/applegpu.py#L1331-L1344) and [FTZ conversion](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L218-L247).

## Parallelism and performance

DOCUMENTED: the test runner normally drives 32 lanes and compares raw register values. This source does not supply a reliable numerical-kernel performance benchmark. [Issue #21](https://github.com/dougallj/applegpu/issues/21) links external microbenchmarks, but its old discussion explicitly retracts certainty about a 32×32+64 instruction; it is not a basis for a Bend limb-multiply throughput claim. No timing tests were run here.

INFERRED: transplant the *test architecture*: immutable U32 input vectors, identical fixed instruction sequence per lane, return raw U32 outputs, compare against an independent exact model. That is an excellent uniform GPU/fork-join shape. Do not port the mutable register emulator wholesale into production Bend. A U32-limb reference model could port selected integer arithmetic; 32×32 products require split limbs or a verified high/low multiply implementation rather than assuming U64 exists. Source basis: [hardware comparison harness](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/hwtest.py#L34-L122).

## Known failures, limitations, war stories

- DOCUMENTED recent correction: [PR #65](https://github.com/dougallj/applegpu/pull/65), merged July 1, 2026, found that `fmadd32` writing a 16-bit destination first rounds to F32 and then to F16. The patch changes FMA, add and multiply modeling and adds `DOUBLE_ROUND_INITIAL_STATE` vectors. It was encountered while setting up M3 tests. This does **not** mean an F32-destination FMA is a nonfused multiply then add; the extra rounding concerns narrowing the result to half. [Patch](https://github.com/dougallj/applegpu/pull/65/files).
- DOCUMENTED maintainer statement: [issue #62](https://github.com/dougallj/applegpu/issues/62#issuecomment-2653000818), February 12, 2025, says M4 is not yet supported and M3/M4 have major ISA changes including instruction encoding; points to a WIP branch. Do not treat the README's G13 target or the later M3-related fix as full M4 support.
- DOCUMENTED: [issue #61](https://github.com/dougallj/applegpu/issues/61) reports an open disassembly assertion with a reproducible binary. [Issue #23](https://github.com/dougallj/applegpu/issues/23) reports stale generated docs; prefer SHA-pinned code for the numerical model. [Issue #30](https://github.com/dougallj/applegpu/issues/30) records instability of the older test replacement API, while current README describes binary archives.
- DOCUMENTED: assembler warns of missing error checking; check its output rather than trusting an accepted instruction string ([README](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/README.md)).

## Relevance for wonky

INFERRED: this is a numerical-platform qualification source, not a Boolean/SSI/fillet algorithm. Use it to make a hardware contract for F32x2 and predicate filters: signed zero, ties-to-even, near-cancellation, true FMA versus contraction, smallest normal and largest subnormal inputs/results, overflow and exact U32↔F32 representability. Add a compiler regression that proves residual operations survive optimization and that operations assumed separate remain separate. None of these tests were executed in this pass.

INFERRED: the proposed biased exponent window 87..167 corresponds to unbiased exponents -40..40, but **this repository does not establish that window is sufficient for wonky's entire F32x2 expression DAG**. Verify all intermediate products, subtraction residuals and rescalings against underflow and overflow, including degree growth in orient3d/point-plane expressions. Integer-only exact fallback is the robust route when a proof or precondition fails. This is especially important for analytic B-rep recovery, where one wrong sign changes topology, whereas bounded mesh deviation alone says nothing about arithmetic classification. Sources motivating this restriction: [fma.py FTZ model](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/fma.py#L194-L247) and [test coverage caveat](https://github.com/dougallj/applegpu/blob/4c5bae61086b8067231120c98b4756d7696d399c/hwtest.py#L10-L15).

## Verdict: learn-from

Use the code and hardware-test method to qualify Bend/Metal numerics and learn exact FTZ/rounding hazards. Do not adopt it as a production geometry dependency or substitute its emulator for an official all-generation hardware guarantee. The seed's universal 'every F32 op flushes' and certified-safe exponent-window conclusions were too strong; RTNE is documented in the model, while local hardware conformance remains untested.
