# W4: frozen Onshape inputs (integration run, 2026-09-23)

W4 is cluster 1 of the triage, `fs-module-import`: 96 corpus files (38
families, 274 units) import Onshape Part Studios at fixed revisions, and the
only way to resolve them was a `modules.json` next to the file. Stage 1
(revision-bound loader in `src/modules.mjs`) and stage 2 (the bridge capture
into `var/onshape-store/` and one generated manifest per corpus file) are
described in [../onshape-inputs.md](../onshape-inputs.md), which also holds
the capture log. The failure analysis and the fix design are in
[cluster-fs-module-import.md](cluster-fs-module-import.md).

This page records the integration: the corpus runner now uses the store
manifests, and the whole cluster was run through it.

## Runner change

`scripts/corpus/run.mjs` (and `scripts/corpus/probe.mjs`, its diagnostic
probe) pick the frozen inputs of an FS unit like this:

1. a sibling `modules.json` next to the corpus file: the CLI reads it by
   itself, as before;
2. otherwise `var/onshape-store/manifests/<corpus path>.json`, when
   `scripts/snapshot-modules.mjs manifests` wrote one: the runner passes it
   with `--modules`;
3. otherwise nothing: the unit runs exactly as before.

The anchor (`fixtures/r10b/r10b.fs`) keeps its fixture manifest. Every record
names the manifest it used in `modules: { source, path, sha256 }`.
`--no-store-manifests` restores the pre-W4 behavior for A/B runs. The corpus
is still only read; the manifests are regenerated by
`node scripts/snapshot-modules.mjs manifests --all`.

**D1: 8 bodies of one revision are recorded under file names that do not
exist.** In `revisions/onshape-id-019892ef@onshape-id-304e7584`
(`ctxBase` of the r20 probes), `revision.json` lists `ZusDD`, `ZgwDD`,
`Zw4DD`, `Zy5DD`, `ZQ6DD`, `ZG7DD`, `ZZ7DD` and `Zy7DD` as
`bodies/<id>.body.json`. The bytes are there, with the right hashes, but under
the case-safe names (`_Zus_D_D.body.json` and so on). Two store manifests
inherit the wrong names:
`cad-project-041/single-step-r20/var/cache/studio-probe-external-1790136693.fs.json`
and `…-1790136717.fs.json`. Neither file is in the cluster run, so the numbers
above are not affected. Loading one of these parts fails with a raw Node
error instead of a named one:

```sh
node bin/wonky.mjs local-development-evidence --check --feature staleBody \
  --param 'partName="P03 R6d wide pull bow - outside GT2 screws"' \
  --modules var/onshape-store/manifests/cad-project-041/single-step-r20/var/cache/studio-probe-external-1790136693.fs.json
# wonky: ENOENT: no such file or directory, open '…/bodies/ZusDD.body.json'
# the same command with partName="T06 R6d 249.2mm rear hopper wall" builds (10 faces)
```

Cause: the twin copy in `captureBody` (`scripts/snapshot-modules.mjs`, around
line 681) writes the bytes to `bodyFile(partId)` but records
`{ ...twin.body }`, which carries the file name of the r10b seed revision
(written before the case-safe names existed). `plan` and `manifests` trust
`revision.json` and do not check that the files exist, so they report this
revision as 17/17 held and `capture --resume` would not repair it. Fix: record
`{ ...twin.body, file, copiedFrom }` in the twin branch; rewrite the 8 `file`
entries of that `revision.json` (the bytes do not change); regenerate the
manifests. Optionally, the loader could turn a missing body file into a named
`fail(...)`.
