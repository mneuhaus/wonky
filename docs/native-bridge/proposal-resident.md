# Native bridge proposal: native-resident bodies behind a narrow session API

Date: 2026-09-22. Bend 2.0.25, Apple M5 Pro (18 logical CPUs), macOS arm64, Node v22.23.1.
Role: architecture proposal. It combines the four measurement reports in this folder
([profile](profile.md), [surface](surface.md), [binding](binding.md), [baseline](baseline.md)) with three small new
measurements (section 17). It builds no kernel and claims no speedup that was not measured. Every end-to-end number
below is an **arithmetic projection** from measured parts, generated by `scripts/native-bridge/resident-projection.mjs`.
All inputs were measured on a shared machine at load average 11.6 to 15.2 on 18 cores, so they are indicative.

## 0. Verdict

1. **In-process embedding works, so this design builds on it.** The binding stage ran Bend-emitted C inside Node as a
   plain N-API addon: 0.5 µs per empty call, bit-exact with the JS target, and as fast as a standalone native
   binary. It also proved **heap residency on the real kernel**: `subtract` kept its result in the Bend heap, that
   body fed `union` directly, and the result was bit-exact with the JS chain (`kernel-t1.json`, `chain`). The
   out-of-process service costs 22 to 29 µs per call and 26 ms per MB. It stays an optional isolation layer, not the
   binding.
2. **Residency is not a speed feature, and this proposal does not sell it as one.** The native chain and the same
   chain routed through JS differ by less than 1 % (1521 vs 1501 to 1513 ms). Marshaling costs under 1.5 ms per heavy
   operation. The speed comes from two other sources, and neither depends on residency:
   - native execution: k = 8.3 to 9.7 at 1 thread and 12.8 to 15.3 at 6 threads on the four measured planar Boolean
     calls;
   - not loading the Bend-compiled JS kernel: 745 to 806 ms per CLI run.
3. **What residency buys:**
   - **Exactness by construction.** `nativeChainExact: false` goes away because nothing is decoded and re-encoded
     between operations.
   - **A smaller host.** The 27 host precision sites, `encodeAnalytic` and `classificationInput` leave the production
     path, and so does the 121-ADT refeed surface.
   - **A home for per-body kernel state.** Prepared solids, caches, and later native multi-operation pipelines can live
     on the resident body.

   What it costs: handle lifetime management, two representations per body (native body plus JS view), and losing
   every resident body when the runtime is poisoned. A simpler alternative gives the same exactness without handles:
   JS keeps each body's exact reply words and sends them back (section 3). The JS-facing API below works with either
   implementation, so that choice can be revisited without touching the frontends.
4. **Lifetime is explicit: a session per build.** Garbage collection plays no part inside a build. JS finalizers do
   not run while the interpreter is synchronous. Measured: 0 of 40,000 `FinalizationRegistry` callbacks ran during a
   synchronous phase with 20 forced GCs, and all 40,000 ran after one event-loop turn
   (`out/native-bridge/resident/finalizer-timing.json`). Finalizers are only a leak backstop for long-lived
   processes.
5. **Projected end-to-end CLI speedups** (details in section 7). These are arithmetic on measured parts, not
   measurements, and every production kernel entry must be native with the JS kernel never loaded:

   | Workload | Today | Native, 1 thread | Native, 6 threads |
   |---|---:|---:|---:|
   | build123d planar-union, planar-pocket, frame-with-tab | 2.7 / 4.3 / 13.9 s | 7.9 to 8.5x | 9.7 to 12.2x |
   | FeatureScript fuse-g1, cut-h1 | 2.3 / 6.2 s | 8.1 to 9.0x | 10.4 to 13.4x |
   | Small models: bracket, bored-spacer | 0.84 / 0.87 s | 7.4x / 6.6x | same |
   | r10b | 55 s | **blocked** | blocked |

   - The small models gain only because the JS kernel load disappears. Their kernel work is negligible.
   - r10b is blocked because its curved-intersection path cannot be emitted as C: Bend 2.0.25 fails with "an arity
     over 255" in the kernel itself.
   - The first shippable step, with only the planar Boolean native and the JS kernel still loaded, projects 2.4 to
     5.2x on the Boolean-heavy runs and 1.0x on small models.

## 1. What the evidence allows, and what it forbids

| Finding (source) | Consequence for this design |
|---|---|
| Direct call `corpus_eval` on a bound FID, 0.5 µs floor, about 6 to 7 ns per U32 word per direction (binding) | Per-operation overhead is irrelevant. A synchronous, operation-level API is enough. |
| One runtime per addon and process, all state `static`, calls serialized by a mutex, `init` once (binding) | One `Kernel` per process. Sessions share it. worker_threads cannot run builds in parallel in one process (4 workers: 159 ms against 114 ms sequential). |
| Only defs reachable from `main` that keep their own FID can be bound. Non-recursive Data parameters are split into slots, and results wider than one word are refused (binding: `KOut` became 12 slots, `WL_RESW` 51) | Every bound def takes and returns `List<...>`, and there are only five bound defs (section 4.3). Opaque residents cross as list-boxed terms. |
| Handles: consumed linearly, `dup` shares by reference count, stale handles give `BX_HANDLE`, fixed table of 4096 (binding, `bx_addon.c`) | The driver borrows (`term_keep`) instead of consuming. The table grows and carries generation, session and epoch. |
| Fail-stop on the calling thread becomes `BX_FAILSTOP`; on a pool worker the process exits 1 (binding) | Threads policy and failure table (sections 9 and 10). |
| 85 production entries, 108 call sites; the interpreter is fully synchronous; queries read decoded bodies, never the kernel (surface) | Every body-producing operation returns a view (summary) synchronously. |
| 27 host sites lose F32x2 low words; 131 of 9,784 result Reals change on the host round trip (surface) | Views are output-only. Nothing may re-encode them (section 8). |
| 84/85 production entries emit C (12 MB, 16 s); `curved-intersection.intersect` and `section.section` fail with "an arity over 255" in the kernel itself (surface) | r10b cannot run natively until the kernel or the compiler changes. A native build lists that branch as unavailable and refuses it loudly. |
| Kernel 64 to 98 % of wall time on Boolean runs; Bend JS load 745 to 806 ms per CLI run; everything else in JS 1.1 % at most (profile) | Keep the frontends in JS. A native run must never import the JS kernel. |
| Out-of-process: 22 to 29 µs per call, 26 ms per MB, blocking client needed (baseline) | Out-of-process only as optional crash isolation for long-lived hosts (section 10). |

## 2. Architecture

```
bin/wonky.mjs · bin/wonky-python.mjs · review server               (JS, unchanged role)
  └─ src/index.mjs build() · src/python.mjs buildPython()
       └─ ModelingContext / Python shape session
            records hold Body refs: { opaque ref, summary, lazily pulled view, JS-owned metadata }
            │  synchronous calls, about one per modeling operation
            ▼
  src/native/kernel-api.mjs       openKernel() → Kernel → Session → ops · view · release · close
            │  request: Uint32Array (generated JS encoders)    reply / view: Uint32Array (generated JS decoders)
   ┌────────┴──────────────────────────┬─────────────────────────────────────┬──────────────────────────┐
   ▼ native                            ▼ js (reference)                      ▼ diff
 .tools/wonky-native/<key>/            kernel/service/api/**/*.bend          runs js and native per op,
   wonky-kernel.node (N-API)             compiled to JS per op module          compares reply and view
   ├ ref table (C): slot → Term          (bend-js-cache), loaded lazily        words bit for bit
   │   + generation, session, epoch    ref table (JS Map), same semantics
   └ FIDs: api · out_reply · out_take
     · view · api_info → Bend C of
     kernel/service/api + kernel/**
```

Both backends speak **one wire**. The JS encoder turns the request into words, Bend decoders read them, the
operation runs, and Bend encoders produce the reply and view words, which the JS decoder reads. The two backends
differ only in the compile target of the Bend code in the middle. Differential testing therefore compares words, not
decoded objects.

The FeatureScript interpreter, the build123d shim, units, record and lineage management, queries over views, evidence
JSON and the STEP/STL/HTML writers stay in JS. So do the input rules (`validatePolygon`, orientation by `signedArea`,
`plane()` normalization) and the refusal message tables such as `PIERCE_DECLINES`.

## 3. Why resident, and what it does not buy

Three ways to carry a body between two kernel operations:

| | A. Stateless, host view refed (today) | B. Stateless, JS keeps exact reply words | C. Native-resident refs (this proposal) |
|---|---|---|---|
| Chained exactness | lossy (`nativeChainExact: false`) | exact | exact |
| Speed | same | same (resend 900 to 6000 words: ≤ 0.05 ms) | same |
| Host code | 27 precision sites, `encodeAnalytic`, `classificationInput`, 121 ADTs in both directions | request-side ADTs stay; host holds opaque word blobs | request-side ADTs for inputs only; bodies are refs |
| Lifetime | JS GC | JS GC (Uint32Array) | sessions + explicit release; finalizers only as backstop |
| After a runtime fail-stop | nothing lost | nothing lost | all residents lost; rebuild from source |
| Per-body kernel state (prepared solids, caches, native pipelines) | impossible | only by serializing it | natural |
| Diff testing | trivial | trivial | paired refs |

The binding stage's measurement settles the speed question for this kernel. The chained `frame-with-tab` union
takes 1234 ms through a resident handle and 1501 to 1513 ms for the whole chain through JS decode and re-encode, the
same as the 1521 ms of the resident keep-plus-chain within 1 %. Residency is chosen for exactness, host simplicity
and the per-body state column. That column is where a real lever may be: the stalled prepared-solid work
(`out/performance/prepared-solids/STATUS.md`) measured `prepare_loops` at 8.4 to 10.1 % of a planar Boolean. A body
used by several operations could prepare once. That benefit is not measured and not claimed here.

**Kill criterion.** If step 3 (section 13) shows that ref lifetime bugs or paired-ref diffing cost more than they
save, switch the backends to option B. The `Session`/`Body` API in section 4.1 hides which option is in use, so the
frontends do not change.

A Bend-side store threaded through calls (the IO-bridge variant, where the resident state lives inside the parked
`main` loop) also works: +0.3 µs per call in the binding stage. It is not chosen. Releasing one body would mean
rewriting the whole store term, and every operation would route through the IO loop. The C-side table holds each
resident as its own term with its own reference count.

## 4. The API

### 4.1 JS-facing: `src/native/kernel-api.mjs` (new)

```ts
export async function openKernel(options?: {
  backend?: 'js' | 'native' | 'diff',          // default process.env.WONKY_KERNEL ?? 'js'; never inferred
  threads?: number,                            // native only; fixed for the process (the pool is created once)
  build?: 'require' | 'auto',                  // stale native build: 'require' throws BX_STALE, 'auto' rebuilds first
}): Promise<Kernel>                            // the only async step: loader and stale check

interface Kernel {
  info(): { backend, target, apiVersion, apiHash, sourceHash, threads, gpu: false, unavailable: string[] }
  session(label: string): Session              // one per build(), buildPython(), review request
  reset(): void                                // only after BX_FAILSTOP; bumps the epoch, invalidates every session
}

interface Session {                            // all synchronous; inputs are borrowed, never consumed
  extrudePolygon(r: { points: [number, number][], plane: Plane, delta: Vec3, offset: Vec3, box: boolean }): Body
  frustum(r: { first: Circle, second?: Circle, delta?: Vec3, offset: Vec3 }): Body
  sketchLines(segments: LineSegment[]): { profile: Profile, points: SolvedPoint[], uses: Use[] }
  sketchArcs(entities: SketchEntity[]): { profile: Profile, view: SketchView }
  extrudeProfile(profile: Profile, r: { plane: Plane, delta: Vec3, offset: Vec3 }): Body
  transform(body: Body, rows: Mat3, offset: Vec3): Body
  boolean(a: Body, b: Body, op: 'UNION' | 'SUBTRACTION' | 'INTERSECTION', policy: ContactPolicy):
    { bodies: Body[], evidence: NativeEvidence }
  importBrep(source: OnshapeSolid, r: { provenance: Provenance }): Body
  identity(kind: IdentityKind, request: IdentityRequest): IdentitySet     // stateless, strings; phase 1 as today
  stepPcurves(body: Body): PCurveSet
  printMesh(body: Body, deviationMm: number): PrintRings
  displayMesh(body: Body, toleranceMm: number): DisplayMesh               // may stay on the js backend (viewer)
  compareCoaxial(a: Body, b: Body, toleranceMm: number): CylinderComparison
  view(ref: Body | Profile, level: 'summary' | 'full'): View              // cached on the ref
  release(ref: Body | Profile): void                                      // idempotent
  close(): void                                                           // releases every ref of the session
}

class Body {                                   // what records and Python shapes hold
  readonly kind: 'polyhedral' | 'analytic'
  readonly summary: Summary                    // counts, precision, bounds, volume, construction budget, validation flags
  get view(): FullView                         // pulled on first access, deep-frozen, never re-encoded
  get vertices(); get edges(); get faces(); get shell(); get validation()  // today's shapes, over the view
  id; name; appearance; identity; operationHistory; constructionBudget; provenance; referenceMeasurements  // JS-owned
  toJSON()                                     // today's brep.json body shape, unchanged
}
```

A refusal throws `KernelRefusal { code, stage, detail }`. It is not a `FeatureScriptError`. The adapter that knows
the source location turns it into `unsupported(message, loc)` with today's message tables. An adapter that forgets
to do so still fails loudly, because the interpreter's `catchable` only accepts `FeatureScriptError` minus
`UnsupportedFeatureError` (`src/interpreter.mjs:35`).

### 4.2 Native: `wonky-kernel.node` exports (extended `src/native/binding/bx_addon.c`)

```c
init({ threads, gpuMB? })            -> info            // once per process, else BX_ONCE
info()                               -> { sourceHash, apiHash, apiVersion, bend, cc, flags, bangs, threads, gpu,
                                          ops: [name...], unavailable: ["boolean/curved-intersection", ...] }
call(op: u32, session: u32, inputs: Int32Array, request: Uint32Array, context: string)
                                     -> { status: u32, reply: Uint32Array, made: Int32Array }
view(ref: i32, level: u32)           -> Uint32Array
release(refs: Int32Array)            -> released: u32
closeSession(session: u32)           -> released: u32
stats()                              -> { live, sessions, epoch, calls, heapBytes, maxRssBytes }
reset()                              -> { epoch }        // also madvise(MADV_DONTNEED) on touched lane stacks (new)
```

What `call` does:

1. Under `bx_lock`, validate every input ref by epoch, session, slot and generation.
2. `term_keep` each resident term, which is a reference-count share and costs O(1).
3. Cons the kept terms into a `List<List<Resident>>` in the heap.
4. Copy `request` into a `List<U32>`, as `bx_list` does today.
5. Record `context`, then evaluate the `api` FID with `corpus_eval`.
6. Read `out_reply` from a `term_keep` of the result.
7. For each made resident `i`, bind `out_take(keep(out), i)` to a new ref.
8. Sink `out`.

Steps 6 and 7 are about 0.5 µs each. `context` names the operation and its FeatureScript source location. The
driver prints it if a pool worker fail-stops (section 9).

### 4.3 Bend: `kernel/service/api/` (new)

```
# types.bend
type Resident is Data:
  RBody{body: Body}
  RProfile{profile: Profile}                       # sketch-lines / sketch-arcs solutions
type Body is Data:
  Polyhedral{solid: T.Solid, measures: Measures}   # the F32 topology.bend path, reported as F32 as today
  Analytic{solid: A.Solid, domains: List<&2, F.DomainChoice>, budget: R.Real,
           tolerances: List<&2, R.Real>, primitive: Primitive, measures: Measures}
type Primitive is Data:
  NoPrimitive{}
  Frustum{bottom: P.Vec3, top: P.Vec3, r0: R.Real, r1: R.Real}   # coaxial, pierce, compare
type Measures is Data:
  Measures{volume: Maybe<&2, R.Real>, bounds: Maybe<&2, A.Bounds>}
type Out is Data:
  Out{status: U32, reply: List<&2, U32>, made: List<&2, Resident>}

# native.bend: GENERATED root, the only file with main (keeps the five defs reachable and FID-bearing)
def api(op: U32, inputs: List<&2, List<&2, Resident>>, request: List<&2, U32>) -> List<&2, Out>
def out_reply(out: List<&2, Out>) -> List<&2, U32>
def out_take(out: List<&2, Out>, index: U32) -> List<&2, Resident>
def view(ref: List<&2, Resident>, level: U32) -> List<&2, U32>
def api_info() -> List<&2, U32>                    # [API_VERSION, op count, view schema]
```

- Each operation lives in `kernel/service/api/ops/<op>.bend`, with a `type <Op>Request is Data` and a def from
  inputs and request to `Out`.
- The generator (`gen-wire.mjs`, extended) writes the request and reply codecs, the `api` dispatcher (`match op`),
  and the view encoders.
- Every bound signature is list-boxed, which is the only shape the binding stage could bind reliably. The generator's
  width estimate must keep `Body` under 255 flat words. The surface stage estimated at most 124 words for the whole
  production closure.

Operations absorb the host logic the surface stage identified:

- **Boolean branch selection.** Today `booleanInBend` reads face and edge types, the cylinder primitive, budgets and
  `curveRange` from the decoded body to pick a branch.
- **`classificationInput`**, with its field validation and domain choices.
- **The vertex residual checks of `validateAnalytic`**: 16,704 calls in the eight profile runs, which become one
  in-kernel pass.
- **The numeric part of `importOnshapeBody`**: surfaces, curves, residuals, periodic seams, arc ranges and assembly,
  which is 18,604 calls down to one per part for r10b. JSON structure checks and id maps stay in JS.
- **The transform measure carry-over.**
- **Pierce axis, radius and reach.** They are computed in binary64 JS today (`src/boolean.mjs:112-121`), which also
  pulls a geometric computation back into Bend.

### 4.4 Wire and view layout

- **Words.** The wire is a flat stream of little-endian U32 words, as in `surface.md` section 7.
  - `F32` is 1 word, its bit pattern. `Real` is exactly 2 words, `bits(hi), bits(lo)`.
  - `Bool` is 0 or 1. `String` is a count followed by one word per code point.
  - A List is a count followed by its elements. A `Maybe` is a tag word followed by the value.
  - An ADT has a tag word when it has more than one constructor, then its fields in declaration order.
- **Status words:**

  | Status | Meaning | JS side |
  |---|---|---|
  | 0 | ok | |
  | 1 | malformed request | `NativeKernelError BX_ARGS` |
  | 2 | unknown op | `BX_ARGS` |
  | 3 | wrong resident kind or input count | `BX_ARGS` |
  | 4 | refused; reply carries `code, stage, detail` | `KernelRefusal` |
  | 5 | audit failed; reply carries the audit words | `fail()` |
  | 6 | unavailable in this build (op or branch not compiled for this target) | `UnsupportedFeatureError` naming the backend |

- **Reply of a body-producing op:** `n`, then `n` summaries. For `boolean` it adds the evidence words: method,
  status, stats, native source budget, input budgets and audits.
- **Summary view (level 0), about 40 words:**
  - kind, precision, V/E/F counts;
  - volume and bounds as `Maybe<Real>` and `Maybe<Bounds>`;
  - construction budget;
  - validation flags and the maximum residual.
- **Full view (level 1):** the `A.Solid` or `T.Solid` words, domains (`curveRange`), tolerances and primitive. The
  JS decoder builds today's decoded body shape from it, with coordinates as `hi + lo` doubles, and adds a
  non-enumerable `exact` accessor for the Real words that evidence needs (`constructionBudget.nativeCeiling`).

## 5. Ref lifetime, invalidation and garbage collection

**Ownership rules:**

1. Every ref belongs to exactly one session. There is one session per `build()`, per `buildPython()` and per
   review-server request. Frozen-module contexts (`src/modules.mjs`) use their build's session.
2. Operations borrow their inputs. JS never sees Bend's linearity. A body can feed any number of operations, as
   `keepTools`, patterns and Python's persistent shapes need.
3. The owner releases a ref where its JS record dies:
   - In `opBoolean`, `records[0].body = first` replaces the target and `records.delete(records[1].key)` removes the
     tool (`src/library.mjs:264-269`). Both release their refs.
   - A failed operation releases the refs it produced.
   - `session.close()` runs in `build()`'s `finally`.
   - The CLI keeps the session open until exports (STEP pcurves, print mesh) are written. `build()` gets
     `{ session }` or returns `model.close()` for that.
4. A ref is `slot (24 bit) | generation (8 bit)` plus the session id. The runtime has an epoch. Any mismatch gives
   `NativeKernelError BX_HANDLE`. A stale ref can never reach another body. The table grows up to 2^24 live refs;
   today's fixed 4096-slot array goes away.
5. **Finalizers:**
   - Each `Body` or `Profile` wrapper is registered in a `FinalizationRegistry`. The callback only pushes the ref to a
     JS queue. The queue is flushed with one `release()` call at the start of the session's next native call, or at
     `close()`.
   - N-API finalizers (`napi_wrap`) are not used. They could run in a GC context while `bx_lock` is held.
   - As measured in section 0, finalizers never run inside a build. They reclaim refs that a long-lived host (review
     server, viewer, test runner) leaked across event-loop turns. Memory within a build is bounded by explicit
     release plus today's limits of 128 bodies and 20,000 operations per feature.
6. `reset()` is allowed only after `BX_FAILSTOP`. It bumps the epoch, so every ref and session becomes invalid, and
   the host must rebuild the model from source.
7. **Memory.** Bend frees on the last reference; it has no GC pause. RSS does not shrink: the heap is an 8 GiB
   virtual reservation that grows in place, and a deep recursion left RSS at 2092 MB after `reset()`. The driver adds
   `madvise(MADV_DONTNEED)` for touched stacks on reset. A long-lived host resets between requests when RSS passes a
   threshold; that is 0.1 ms, and all sessions are closed at request end anyway.
8. **Two copies per body:** the Bend term and the JS view. For the planar cases, native-only processes ran at 76 to
   86 MB RSS (`kernel-t6/t18.json`), against 225 to 267 MB maximum RSS for today's JS-kernel CLI runs.

**Views are pulled eagerly in phase 1, and that is honest.** `identity.geometryRevision(body)` hashes the full
decoded geometry of every body after every operation (`src/identity.mjs:21`). `operationEvidence` does the same for
every input and output. As long as revisions are defined that way, every body needs its full view, which costs 0.1
to 0.9 ms per heavy operation (binding `decodeMs`). Lazy full views only pay off after revisions become a native hash
over view words. That changes the revision strings in `brep.json`, so it is Marc's decision (section 16). The API
already has the lazy getter, so the switch is local.

## 7. Expected end-to-end speedups

### Method

The basis is the profile stage's attributed buckets, one profiled run per workload:

- T is the total time.
- K is kernel execution plus the JS GC it causes.
- B is the Bend JS load.
- S_start is Node start plus the ESM graph plus B.
- O is the estimated boundary cost.

The native kernel time is **K' = K · (b / k_bool + (1 − b) / k_rest)**:

- b is the planar Boolean share of kernel time, from the count run.
- k_bool is JS-target p50 over native p50 on **the same captured calls in the same process**, bit-exact
  (`kernel-t1.json`, `kernel-t6.json`).
  - At 1 thread: planar-union 9.72, planar-pocket 9.18, frame-with-tab 9.25 and 8.34.
  - At 6 threads: 14.55, 14.35, 15.27 and 12.81.
  - fuse-g1 and cut-h1 were not captured. Their range is extrapolated from the union and subtract calls above.
  - The JS p50 includes the GC during the call, like K.
- k_rest covers audits, measures, identity, residuals and pcurves, which have no native timing. The central case
  takes k_rest = k_bool. The pessimistic column takes k_rest = 1 and an addon load of 20 ms.

Assumptions:

- Addon load and init: 1 ms. The planar addon measured 0.73 ms plus 0.07 ms warm. A full-surface addon has not been
  measured.
- Stale check: 5 ms. The upper bound measured 1.4 to 1.6 ms median and 3.2 to 4.4 ms on the first run (section 17).
- Host work that stays in JS is T − K − B, unchanged: Node start, the src module graph, parse or Python bridge
  (including the Python subprocess wait), interpreter, host adaptation, export and idle time.

The scenarios:

- **S1:** only the planar Boolean calls are native. The API stays fine-grained and the JS kernel is still loaded:
  `T − K·b + K·b/k + measured encode/decode + load`.
- **S3:** every production entry is native, and neither the JS kernel nor `bend-loader` is loaded:
  `T − K − B + K' + load + stale check + O`.
- **Resident:** startup already paid, as in a review server or test runner: `(T − S_start) / (T − S_start − K + K' + O)`.

Indicative wall times scale the projection to the plain-run median.

## 8. Exactness guarantees

1. **Inputs are rounded once, at the API boundary, by today's rules.**
   - FeatureScript and Python binary64 values become Real through `real()`: hi = fround(x), lo = fround(x − hi),
     |x| ≤ 1e20, no F32 underflow.
   - The declared F32 polyhedral path uses `Math.fround`. That is input serialization, and the reported precision
     stays `F32`.
2. **No binary64 on the wire.**
   - F32 crosses as its bit pattern; a Real crosses as two bit patterns.
   - The binding stage measured 21 special values and 4096 F32x2 words round-tripping unchanged: −0, the smallest and
     largest subnormal (the CPU path does not flush to zero), infinities, and NaN payloads.
   - NaN payloads are not canonical. A signaling NaN stays signaling natively and becomes quiet in JS. Comparisons
     treat NaN as a class, and a NaN in any geometry view fails validation.
3. **Chains stay in the kernel.** Operation inputs are refs, so no host decode and re-encode sits between two
   operations on either backend. `nativeChainExact` becomes true by construction. After the migration, the 27
   precision sites reduce to input-serialization sites and output (view) sites. An extension of `surface-scan.mjs`
   fails if any production path can still re-encode a view (`encodeAnalytic`, `real(number(...))`,
   `classificationInput`).
4. **Equality across targets is tested, not assumed.**
   - Measured: the four captured planar calls are word-identical to the JS target at 1, 6 and 18 threads, and so is
     the resident chain.
   - Risk: clang may legally fuse multiply-add, which would break double-word arithmetic (the emitted C does Dekker
     splits with `4097.0f`; see `kgen/kernel.c:2978`).
   - The native build therefore pins `-ffp-contract=off`, forbids `-ffast-math`, records the flags, and runs a
     two-product/renormalization canary on adversarial inputs before it accepts the binary.
   - Metal's device program is compiled with `MTLMathModeSafe` (emitted C, `gpu_make`). Its subnormal and FMA
     behavior still needs a diff test per op before any op is routed to the GPU.
5. **Views are output-only.** Doubles in views (hi + lo) feed queries, exports and evidence. The exact Real words are
   available through `view.exact` where evidence needs them.
6. **Behavior change, and a one-time review.** Once chains stay resident, the last bits of multi-operation results
   change compared with today; 131 of 9,784 replayed result Reals already differ on the round trip.
   - The review is done on the **JS reference**, so it does not depend on native code.
   - A script lists every golden output and revision string that changes.
   - Marc approves the list before goldens are rewritten.

## 9. Failure semantics

| Event | Detected by | JS sees | Process | Refs |
|---|---|---|---|---|
| Capability refusal (`Refused` in Bend) | reply status 4 | `KernelRefusal`, turned by the adapter into `UnsupportedFeatureError` at the FeatureScript source location with today's message; not catchable by `try`/`try silent` | runs | inputs intact, no outputs |
| Op or branch not in this build (native curved intersection) | status 6, or `info().unavailable` before the call | `UnsupportedFeatureError`: "opBoolean curved intersection is not available in the native ARM64 build (Bend 2.0.25 'an arity over 255'); run with --kernel js" | runs | intact |
| Result audit failed | status 5 | `FeatureScriptError` via `fail()`, as today | runs | partial outputs released |
| Malformed request, unknown op, wrong kind | status 1 to 3 | `NativeKernelError BX_ARGS` (a bridge bug, not a model error) | runs | intact |
| Stale, released or foreign ref | driver | `NativeKernelError BX_HANDLE` | runs | none |
| Fail-stop on the calling thread (threads = 1, CPU build without `!`): Nat overflow, stack overflow, heap exhaustion | `siglongjmp` in the driver | `NativeKernelError BX_FAILSTOP` with the runtime's `bend: ...` text and the op context; later calls get `BX_POISONED` until `reset()` | runs | all invalid (epoch) |
| Fail-stop on a pool worker (threads > 1, or any `!` in the module) | runtime `_exit(1)` | nothing | **exits 1**; stderr `bend: <reason>` plus `bend-binding: fail-stop in pool worker during boolean (model/..., r10b.fs:25:2)` | none |
| GPU OOM (Metal variant only) | calling thread | `BX_FAILSTOP`; `reset()` 8 ms | runs | invalid |
| Addon missing or stale, `apiHash` or arch mismatch, `dlopen` error | loader, before any modeling | `NativeKernelError BX_LOAD` / `BX_STALE` / `BX_ABI`, with the rebuild command | CLI exits 1 | none |
| Diff mismatch | diff backend | `NativeKernelError BX_DIVERGENCE`: op, context, first differing word, both values, path of a replay bundle | runs | none |
| Kernel never returns | nothing in-process (a synchronous call cannot be interrupted from JS; kernel recursion consumes fuel Nats) | none | Ctrl-C ends the process | isolation child if needed |

**Invariant:** no native failure is ever re-run on the JS target. The diff backend runs both targets because it was
explicitly selected, and it fails when they disagree. The static routing of step 1 (planar Boolean native, the rest
on JS) is a declared configuration recorded in `backend.target`. It is not a runtime decision.

## 10. Threads and Metal routing

**Threads.**

- The CPU addon is built with no `!` anywhere in the API closure; the build asserts `BANGS == 0`. At `threads = 1`
  every fork-join runs solo on the calling thread, so every runtime fail-stop becomes a catchable `BX_FAILSTOP`.
- Measured: 6 threads give 1.50 to 1.65x on the four planar calls, and 18 threads add almost nothing.
- **CLI default: 6 threads** (`wonky`, `wonky-python`).
  - A pool-worker fail-stop ends the process with exit 1 and the op context on stderr. That is loud, as AGENTS.md
    requires, and a CLI loses nothing by it: `build()` fails before any export anyway.
- **Long-lived hosts default to 1 thread**: review server, viewer, test runner.
  - If one of them wants threads, it runs the kernel in an isolation child: the baseline service, which restarts in
    2 ms. The 22 to 29 µs per call are irrelevant at one call per operation.
- The clean fix is upstream: a CPU variant of the runtime's existing cooperative `H_ERROR_CODE` path. With it, both
  defaults become 6.

**Metal.**

- Metal is not in the production addon. No API operation has a `!`, and neither does the planar Boolean.
- Metal would add 31 to 35 ms of device initialization per process and 0.26 to 0.65 ms per dispatch, for no gain.
- A Metal variant (`--kernel native-metal`, separate cache key, `.gpu` archive next to the `.node`) becomes eligible
  for an operation only if:
  1. its Bend implementation has deliberate `!` call sites over well-partitioned independent work. Badly partitioned
     Metal was 35x slower than the CPU in `hardware-performance.md`;
  2. it wins end to end, device initialization included, in the kind of process it runs in. Resident sessions
     amortize the initialization; a CLI run does not;
  3. diff mode shows it bit-exact against the CPU and JS targets;
  4. its build finishes within a bounded time. The build123d workload's Metal build was killed after 911 s.
- Routing happens per process, when the variant is chosen, and per call site inside Bend (`!`). JS never routes an
  individual call to the GPU.
- Plausible candidates are batched coaxial or pierce Booleans and a batched ray classification. Today's single
  planar Booleans are not.

## 11. Native build and caching

**`scripts/native-bridge/build-native.mjs`** (future step). It is fully scripted; generated files are never edited.

1. Resolve the import closure of `kernel/service/api/native.bend` in one pass, using the same lexer rules as
   `bend-loader`.
2. Compute the **key** as sha256 over:
   - the sorted (path, sha256) pairs of the closure;
   - the generator and build scripts;
   - `bx_pre.h` and `bx_addon.c`;
   - `bend.lock.json`;
   - the compiler binary sha256, checked at build time against `bend.lock.json` `sha256.darwin-arm64`;
   - `clang --version`, the flags (`-std=c11 -O3 -fPIC -ffp-contract=off`), the target (cpu or metal), the arch and
     the N-API version.
3. Generate codecs and the dispatcher, then run `bend native.bend -o native.c` and `native_ops.h`. Compile the one
   translation unit (`bx_pre.h` + `native.c` + ops + `bx_addon.c`) with `-DBX_SOURCE_HASH=<key>
   -DBX_API_HASH=<hash>`.
4. Refuse the binary unless every check passes:
   - FIDs present, arities match, all signatures list-boxed;
   - `BANGS == 0` for cpu;
   - no width warnings;
   - the FP canary passes in a child process;
   - a small captured corpus replays bit-exact against the JS reference.
5. Write to `.tools/wonky-native/<key>.tmp/` and rename it to `<key>/` atomically, with a `manifest.json` that holds
   the key inputs, versions, flags, per-step times, the load average, ops and unavailable branches.
   - A lock file allows one native compile at a time, as the shared-machine rule requires.
   - Keep the last three keys.

**Loader (`backend-native.mjs`).**

- Recompute the source part of the key. The measured upper bound over all 72 kernel files is 1.4 to 1.6 ms median.
- For the compiler, hash `bend.lock.json` plus a stat record (size, mtime, inode) of the 64 MB binary; rehash the
  binary only if the stat record changed.
- Compare with the manifest, `dlopen`, then compare `info().sourceHash` and `apiHash`.
- Any mismatch gives `BX_STALE` with the changed files and the rebuild command. **A stale binary never runs.**
- `build: 'auto'` runs the build synchronously with printed progress, then loads. If the build fails, it is an error,
  never the JS target.

**Build cost.**

- Measured: the planar-only addon took 12 s (bend 4.7 s + clang 7.2 s, load about 13); C emission of 84 production
  entries took 16 s for 12 MB of C.
- Not measured: clang on that 12 MB translation unit, which will dominate; the binary size; and its first and warm
  load. Step 0 measures them.

## 12. Dev-loop ergonomics

- **Editing kernel Bend: `--kernel js`,** the default for tests.
  - Each API operation is its own module and is compiled separately through `bend-js-cache`. A kernel edit
    recompiles only the operation modules whose closure contains the file, and only when they are used.
  - A single `api.bend` compiled to JS would be a regression: the full generated closure took 394 s cold as one unit.
- **Running real models: `--kernel native`,** with `WONKY_NATIVE_BUILD=auto` in dev shells. After an edit, the next
  run rebuilds, printing what changed and how long it took. It never falls back silently.
- **Checking an edit on both targets: `--kernel diff`** on focused tests and models.
- **Zero setup stays:** a fresh clone runs on js after `npm run setup`. Native needs Xcode's clang and Node's headers,
  as the binding build does today, and no npm dependencies.
- **Profiling native code:** V8 CPU profiles show the addon as one opaque frame. Use `sample` or Instruments on the
  Node process with a FID-to-Bend-definition symbol map emitted at build time.
- **Benchmarks stay separate**, as AGENTS.md requires: cold start, warmed operation, frontend, validation and export,
  each with `uptime`.

## 14. Testing

1. **API conformance** (`test/native-bridge-api.test.mjs`), run against every available backend:
   - borrow semantics, release, double release, closed sessions, generations and epoch;
   - status mapping, malformed requests, deterministic views;
   - input views are unchanged after an operation. This also checks the assumption that the Bend JS target never
     mutates argument objects, which today's host already relies on: 24 to 43 % of argument nodes are earlier
     results.
2. **Model matrix.** `scripts/native-bridge/test-matrix.mjs` runs named focused test files with `WONKY_KERNEL=js`,
   `native` and `diff`, and native at threads 1 and 6. It never runs the full suite on a shared machine. Tests that
   assert `backend.target === 'JavaScript'` get a backend-aware assertion.
3. **Differential mode.**
   - Every operation runs on both targets with identical request words.
   - Reply words, made-counts and the words of every view level must be equal. NaN compares by class.
   - A mismatch writes a replay bundle to `tmp/native-bridge/divergence/`: request words plus the input view words.
     `scripts/native-bridge/replay.mjs` can re-run that bundle on either target.
4. **Replay corpus:** `captured.json` and the surface stage's 153 real calls, bit-exact native against stored JS
   results.
5. **Build tests:**
   - editing a kernel file in a temporary copy makes the loader refuse;
   - an embedded hash mismatch is refused;
   - an `apiHash` mismatch is refused;
   - the FP canary runs;
   - the `BANGS == 0` assertion holds.
6. **Failure tests**, reusing the binding stage'project-component-32f60153-process harness:
   - `BX_FAILSTOP` becomes an exception, poisons the runtime and invalidates refs;
   - a pool-worker exit prints the op context;
   - `try` and `try silent` cannot swallow `NativeKernelError` or `KernelRefusal`.
7. **Exactness transition:** re-run the frame-with-tab capture; `nativeChainExact` must be true; the list of changed
   goldens must be reviewed.
8. **Performance** is a benchmark script, not a test. Each phase is timed separately, with load averages.

## 15. Risks

1. **Residency may not pay for itself.** It buys no measured speed. If lifetime bugs or paired-ref diffing cost too
   much, use option B (section 3). The API does not change.
2. **Thin k evidence.** Native k is measured on four planar calls from three inputs on a loaded machine. fuse and cut
   are extrapolated, and non-Boolean kernel code is assumed to speed up by the same k. The pessimistic column
   (k_rest = 1, 20 ms load) still shows 4.8 to 7.6x once the JS load is gone.
3. **r10b, the acceptance target, gains nothing natively** until the curved path compiles to C. The native backend
   must refuse it loudly, never hand it to JS.
4. **A pool-worker fail-stop kills Node.** Mitigations: threads default, op context on stderr, an isolation child for
   long-lived hosts, the upstream runtime fix.
5. **Unmeasured build and load costs of the full addon.** If clang takes minutes, the native dev loop suffers. The
   cache and `--kernel js` for editing contain that.
6. **Bindability depends on Bend's inlining and unboxing choices** (FID missing, parameter splitting). Mitigations:
   five list-boxed defs reachable from a generated `main`, build-time checks, and review whenever the pinned Bend
   version changes.
7. **Two representations per body.** The native body is the truth. Views are frozen and decoded from the same words
   on both backends, and JS-owned metadata never enters the kernel.
8. **Memory.** RSS does not shrink; a deep recursion leaves about 2 GB. Mitigations: `madvise` on reset and periodic
   resets in long-lived hosts.
9. **Kernel churn.** The Boolean bake-off may replace or extend Boolean branches, for example with mesh-backed
   bodies. `boolean` stays implementation-agnostic; new body kinds bump `API_VERSION`.
10. **Golden churn** when chains become exact. It is reviewed once, on the JS reference.
11. **One runtime per process with serialized calls**, so builds cannot run in parallel inside one process.
    Parallelism must come from inside a Bend operation, and nothing measured so far shows it for a single Boolean
    beyond 1.50 to 1.65x.
12. **Silent cross-target FP drift** (contraction, GPU math). Guarded by `-ffp-contract=off`, the canary and diff mode.
13. **The algorithmic gap remains:** about 105x to OCCT on frame-with-tab even at 6 threads.

## 16. Decisions for Marc

1. Residency (option C) with the kill criterion, or option B (JS-held exact words) from the start. My recommendation
   is C, because it gives the per-body state a home, with B kept ready.
2. Threads: CLI default 6 with a loud process exit on pool-worker fail-stops, long-lived hosts 1 or isolated. The
   alternative is 1 everywhere until the runtime fix.
3. Upstream requests to Bend:
   - a CPU variant of the cooperative error path;
   - a library root set other than `main`;
   - boxed call entries per exported def;
   - a packed word buffer type.
4. Identity: a stateless op in phase 1; later a native revision hash, which changes the revision strings in
   `brep.json`, and packed strings, which are 4x smaller.
5. The policy for accepting last-bit golden changes when chains become exact.
6. Whether the viewer's display mesh stays on the JS reference.
7. The native cache location, proposed as `.tools/wonky-native/<key>/` (gitignored like `bend-js-cache`).
